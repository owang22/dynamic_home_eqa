## Measured today (Qwen3-VL-8B on Z690, guidance backend, real 10-26 dog frames)
Prompt: people count, path ahead open/partly_blocked/blocked, ≤4 objects. JSON schema, max 80 tokens. Results for 12 frames:

| frame width | in flight | latency median / max | throughput |
|---|---|---|---|
| 640 | 1 | 0.94 / 0.98 s | 1.1 frames/s |
| 640 | 2 | 0.87 / 1.15 s | 2.2 frames/s |
| 640 | 4 | 0.92 / 0.99 s | 4.3 frames/s |
| 1280 | 4 | 0.91 / 1.00 s | 4.3 frames/s |

- The server runs 8 sequences at once (`--max-num-seqs 8`). A 2 Hz watcher keeps about 2 in flight, so about 6 slots stay
  free for watch_go_to, scan_for, skills and /label/detect. GPU load was 0–13% while idle today.
- Each answer is about 0.9 s old when it arrives. At 0.3–0.5 m/s that's 0.3–0.5 m of walking. That's fine for deciding
  and labelling, but not for collision stops; the lidar and the planner keep that job.
- Sample output: `{"people":1,"path":"partly_blocked","objects":["office chair","drawer unit","printer","computer tower"]}`.
- **Recommendation: keep it on Z690 at 2 Hz** (two requests pipelined, 640 px). The H100 has been showing 503s since
  10-28, and a network hop adds latency to every stop decision.

## Plan
1. **Watcher thread in the console**
   - Runs during go_to, move and turn (and watch_go_to, which reuses it).
   - Frames at 2 Hz, at most 2 requests in flight. If the server is busy, frames are dropped, not queued.
   - Each label goes into the trail record for that frame's time and pose, so memory is labelled as it is written.
   - Labels are also kept in `/history`, for working out afterwards what happened.
2. **Moves that end on events: `interrupt_on=[...]`**
   - The default is empty, so today's behaviour is unchanged.
   - Events: `person_seen`, `blocked_seen`, `target_seen` (needs `look_for`), plus the existing `lost` (pose_suspect).
   - When one fires, the dog stops and the reply carries `stop_reason=<event>`, `event: {t, label, pose}` and the frame
     (path plus a small JPEG, like show_pictures).
   - To avoid false stops, an event needs 2 labels in a row that agree. That costs about 0.5 s more at 2 Hz.
3. **Delivery**
   - The event comes back as the move's own reply, since your server.py already branches on `stop_reason`.
   - The same events go on `/events` (the 10 Hz stream) as a `watch` field, for the console and logs only. Nothing has
     to listen to it.
4. **(Later) camera steering for the last metre.** Agreed it should wait.

## Two changes to your proposal
- **`person` is already taken.** Today `stop_reason: person` means "a person took over control". A person seen on camera
  is `person_seen`; the same rule gives `blocked_seen`. Please use these names in server.py.
- **`arrived` stays as is.** It's already the finish reason for move, turn and go_to, so it isn't a new event.
