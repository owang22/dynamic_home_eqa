# revamp_v1 — revamped simulated households

Created **August 7, 2026**. Stage 1 of the household revamp: narrative
profiles (WHO lives in each home, WHAT objects they own — no clock times).
The previous v1/v22 schedule-spec profiles and built banks are archived in
`../../archive/pre_revamp_2026-08-07/`.

Layout — one subdirectory per generator model, same 10-household spec and
the shared verbatim prompt in `generation_prompt.md`:

- `claude-fable-5/` — generated by Claude Fable 5 (all 10 households done)
- `chatgpt-5.6sol-high/` — generated by ChatGPT-5.6sol, high reasoning,
  pasted in by hand (all 10 households done)

The two sets share household ids, types, and constraints, so `hh_00N` in
one directory is the same slot as `hh_00N` in the other — usable as a
paired comparison across generators.

Each subdirectory has its own `README.md`, a `control.yaml` (household
list, constraints, per-file generation status), and `households/*.yaml`.

## Canonical profile format

Both sets are normalized to one style by `normalize_profiles.py`, so the
two directories differ only in content. Run it after pasting in any new
household:

    python normalize_profiles.py --check   # report, write nothing
    python normalize_profiles.py           # rewrite in place

The script is idempotent, verifies every rewrite round-trips to identical
parsed data before writing, and reports each fix it makes. The style it
enforces:

- **Key order** — `household_id, household_type, residents, relationships,
  home_layout_notes, object_inventory, daily_life_summary, quirks`;
  resident = `id, name, age, occupation, personality, habits`;
  object = `id, class, owner, role`.
- **Block style throughout** — no flow mappings (`{id: ..., class: ...}`),
  no blank lines inside lists, sequences indented under their key.
- **Folded scalars (`>-`)** for the four long prose fields, so colons in
  prose can never break parsing.
- **Plain scalars** for everything else, wrapped at 78 columns. Plain text
  folds on whitespace, so it wraps without the backslash continuations a
  quoted scalar needs. A quoted value in the output therefore marks a real
  parsing hazard, not an authoring habit.
- **Object ids begin with their own `class`** — `medication_bottle_ruth`,
  not `medication_ruth`. The part after the class is a free discriminator:
  an index (`mug_1`), an owner (`phone_lena`), or a descriptive tag
  (`charger_office`). All three appear in both sets by design; only the
  class prefix is mandatory, and ids must be unique within a household.

It also checks what normalization must not hide: duplicate object ids,
owners that name no resident, and residents numbered out of order.

## Stage 2 (pilot): schedules and timelines

Stage 2 turns a narrative profile into hourly object timelines in two
steps, done so far for claude-fable-5 hh_001 (solo night-shifter) and
hh_002 (family of four — the first multi-resident spec):

1. **Schedule spec** (`<set>/schedules/hh_00N_schedule.yaml`) — the
   LLM-compiled clock-time layer: receptacles derived from
   `home_layout_notes`, weekly activity blocks with times, and per-activity
   `during`/`after` object-movement rules derived from `habits`. Each block
   cites the narrative line it encodes. This is the reviewable artifact —
   times and probabilities are judgment calls, so check them here, not in
   the generated output.
2. **Simulation** (`simulate_schedule.py`) — deterministic given
   (spec, seed, days); no LLM in the loop. Realizes blocks with start
   jitter, applies during/after moves, daily `p_misplace` drift, and
   `reset_all` sweeps; verifies the spec places exactly the profile's
   inventory. Output per run: `events.jsonl` (every parent change, with
   cause), `hourly.csv` (one row per hour, one column per object), and
   `meta.json` (move counts).

       python simulate_schedule.py claude-fable-5/schedules/hh_001_schedule.yaml \
           --days 14 --seed 0 --out claude-fable-5/timelines/hh_001_seed0

Timelines are generated artifacts: regenerate rather than edit, and prefer
committing specs (small, reviewable) over timelines (cheap to reproduce).

Timelines can additionally be grounded room-level in a real HSSD scene and
replayed in a topdown web viewer — see `../../visualization/README.md`.
After (re)running `simulate_schedule.py`, re-run the matching
`visualization/spatialize.py` config to restore the spatial fields it adds
to `events.jsonl` (plus `hourly_rooms.csv` and the viewer's `trace.json`).

### Procedure: turning household activities into object routines

This is the method as actually exercised on hh_001 — a record of what we
did and what it cost, not a validated recipe. It has been run on **1 of 20
households**, so treat the step order as settled and the parameter choices
as provisional.

The division of labor is the point: the LLM writes the *spec* (judgment —
times, bindings, probabilities), and a deterministic simulator writes the
*timeline* (bookkeeping — jitter, sampling, carryover). Continuity errors
come from hand-writing 336 hourly states; specs are ~150 reviewable lines
that expand to any number of days and seeds.

**Step 1 — receptacles.** Read `home_layout_notes` plus every surface named
in a habit or an object `role`; each becomes a receptacle with a room. Add
the *landing spots* habits imply but prose never names — a book that
"slides off the bed" needs a `bedroom_floor_*` to slide onto, or the habit
silently has nowhere to go. Naming: `<thing>_<room-initial><n>`.

**Step 2 — placements (homes).** Every inventory object gets a `home`: where
it belongs, and where a tidy-up returns it. This comes from the object's
`role` field, which stage 1 wrote for exactly this purpose. Two modifiers:

- `static: true` — the role says it does not move ("never leaves the
  nightstand", "leans by the door"). A deliberate, declared choice.
- `p_misplace` + `misplace_set` — the role describes drift with no activity
  behind it ("roams the apartment with her and gets stranded mid-room").
  This is the only movement source outside scheduled blocks.

**Step 3 — schedule blocks.** From `household_type`, `occupation`, and
`daily_life_summary`, write each resident's weekly blocks: activity, days,
start, end. Day 0 = Monday; a block whose end ≤ start wraps past midnight.
The narrative constrains *ordering and overlap* ("she comes home around the
time commuters are leaving", who is out when) — the clock times themselves
are invented to satisfy those constraints.

Each activity then gets a **jitter class** — how much its start drifts
day-to-day, calibrated against CASAS free-living homes
(`casas/README.md`): `external` (σ10 — contractual: shifts, commutes,
school runs, and self-imposed rituals the narrative calls strict),
`routine` (σ30 — body-clock: sleep onset, household meals), `flexible`
(σ75 — self-paced: solo meals, home work), `loose` (σ110 — whim: weekend
projects, tidy sweeps). Class assignment is a per-household judgment (the
calibration found a couple whose *dinner* was the tightest anchor in four
homes); only the σ values are data-derived. Overlapping realized blocks
resolve by anchor priority — the tighter class keeps its boundary, so a
drifting evening activity is truncated by a fixed departure, never the
reverse; blocks squeezed to nothing are dropped and counted in
`meta.json` (a few per fortnight = skipped-breakfast realism; a critical
ritual dropping regularly = promote its class). Legacy `jitter_min: N`
(uniform ±N) still works.

On top of the class values, each resident carries a `jitter_scale`
punctuality multiplier (default 1.0, hard-bounded to [0.5, 2.0] so
households stay inside the spread observed across real homes). This is how
messiness/punctuality varies between individuals: hh_002 runs Priya at 0.8
against Tom at 1.3 in the same house, so the same `routine` activity is
tighter for her than for him.

**Tidying is a process, not an instant.** A `reset_all: {p, [objects]}`
activity makes its resident walk the house returning astray items to their
homes, nearest-first from wherever they stand (greedy walk over real anchor
geometry when the simulator gets `--anchors <spatial config>`), each item
taking 2–5 minutes × the tidier's `jitter_scale` — so a messy or
distractible person tidies slower, a 20-minute bout may not reach
everything (`tidy_ran_out_of_time` in meta.json), and events land as
`tidy:<activity>` spread through the bout rather than one burst. `objects:`
scopes the sweep (hh_002's nightly toy sweep) — omit it for a whole-house
reset (hh_001's Saturday mania).

**Locations beyond receptacles.** `ELSEWHERE` = out of the house;
`person:<resident_id>` = carried. Phones have `home: person:<owner>` and
ride along with their owner all day (including out of the house), leaving
the person only by explicit rule (Marisol's bedtime exile to the charger,
Priya's overnight nightstand dock) or by `p_misplace` (Tom's phone set
down mid-house — that IS how phones get lost). Activities declare
`at: <receptacle>` — where they happen — which gives every resident a
position track (`residents.jsonl`), consumed by the spatializer to place
carried objects and draw the residents themselves in the viewer.

**Step 4 — bind habits to activities.** Each habit becomes `during`/`after`
rules on the block where it happens. The translation we settled on:

| narrative language | spec form |
|---|---|
| where an object is *used* during an activity | `during: {obj: receptacle}` |
| where it is *left afterwards* | `after:` rule |
| "always", "the moment she…", ritual language | `{dest: r}` — no branch |
| "usually", "most days", "instead of…" | `{dest: r, p: 0.7–0.9, else: r2}` |
| "wherever X happens to end" | `{dist: {r1: …, r2: …, r3: …}}` |
| leaves the house with her | `{dest: ELSEWHERE}` |
| a whole-home sweep in `quirks` | `reset_all: {p: q}` on that block |
| habit that only applies if the object is already out | add `only_from: [...]` |

Two conventions carry meaning beyond mechanics. `ELSEWHERE` is a real
location, not a null — objects stay there until an `arrive_home`-style
block places them again, which is what makes "who is home when" legible in
the data. And a `reset_all` block is how a *quirk* (Marisol's weekly manic
sweep) becomes a signature in the timeline: the fraction of objects at home
oscillates weekly instead of decaying monotonically.

**Step 5 — lint, simulate, read it back.** `simulate_schedule.py` validates
before it writes: unknown receptacles/objects, distributions that do not sum
to 1, blocks with no activity definition, placements that do not match the
profile inventory exactly, and the reachability lint below. Then run it and
check the *output* against claims in the narrative you did not encode
directly — invariants ("the phone is on the kitchen charger every day at
noon"), oscillations, sink stacking. That read-back is where both pilot bugs
surfaced.

**Invariants the spec must satisfy**

- Every object either can reach ≥2 receptacles, or declares `static: true`.
  An object whose every rule targets the receptacle it already lives at
  produces rules that look alive and are silent no-ops.
- Conversely, a `static: true` object must appear in no activity rule.
- Placements ≡ the profile's `object_inventory`, exactly.

**Judgment calls that stay with the author** — review these in the spec, not
the timeline: clock times and shift pattern; whether the pattern relaxes on
days off; every probability in an `after` rule. None are derived from data
yet. The archived pre-revamp system validated block timing against ATUS
time-use bands and jitter against HOMER routines
(`archive/pre_revamp_2026-08-07/profiles_manual/*.anchor_report.md`); no
equivalent anchor check exists for these specs.

**Lessons from the pilot**

- *Rules fire on state, not just on schedule.* The first draft cleared a
  plate to the sink after every daysleep — including Monday, when no meal
  had happened and the plate was in the cupboard. Hence `only_from`: a rule
  fires only when the object is somewhere the habit implies.
- *A silent no-op is invisible without a lint.* `blanket_1`'s every rule
  targeted `couch_l1`, its own home, so it never moved and never errored.
  The reachability lint now makes immobility a declared choice.
- *Day 0 is a cold start.* Objects sit at their homes until an activity
  first touches them, so early-timeline stillness is expected, not a bug.
  Discard a burn-in day or start mid-week if that matters downstream.
- *Static objects are load-bearing but cost inventory.* hh_001 ends with 4
  of 17 objects declared static. The old v22 design got this effect from
  *extra* distractor objects layered on top of the real inventory; here they
  consume real slots, which is worth revisiting before scaling up.
